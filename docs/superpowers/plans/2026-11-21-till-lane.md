# Till Lane Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** A lane application that opens a window in the Cloud & Azure skin, takes a
scan, prices it, totals it, takes tender, and prints a receipt — on a desk, with no
hardware attached.

**Architecture:** A new `till-lane` binary crate in the existing `till/` workspace.
The sale lives in `LaneState`, which is **egui-free** and therefore unit-testable
without a window; the UI layer only renders it and feeds it events. Every device —
printer, scanner, scale, drawer — and the fiscal endpoint sit behind traits with
simulated implementations, so the whole flow runs in CI.

**Tech Stack:** Rust 2024, `eframe`/`egui` (latest stable), the already-merged
`till-core` and `till-store`, `tokio` for the store's async API, Inter and JetBrains
Mono embedded as TTFs.

**Spec:** `docs/superpowers/specs/2026-11-21-till-ui-toolkit-design.md`, which amends
`docs/superpowers/specs/2026-11-20-supermarket-retail-design.md` §6.3, §6.4 and C9.
Read both.

## Global Constraints

- Whole-franc rounding at the **line**; tax keeps 2 decimal places. RWF has no
  circulating subunit.
- Header tax is the **sum of the line taxes**, never recomputed from a band total.
  `BasketTotals` already does this; the lane displays it and never re-derives it.
- `sqlx`'s `macros` feature stays disabled. The build never needs a live database.
- Currency RWF, timezone Africa/Kigali.
- **C1:** the lane hard-stops when the fiscal port is unreachable. Offline selling is
  prohibited; this is not a degraded mode to trade through.
- **C5:** the receipt carries the `SDC INFORMATION` block — Date, Time, SDC ID,
  RECEIPT NUMBER, Internal Data and Receipt Signature, the last two dashed every 4
  characters — plus the CIS receipt number and the MRC. `COPY`, `TRAINING` and
  `PRO FORMA` must be visually distinguishable from `NORMAL`.
- `Money` and `Qty` expose **no public Decimal accessor**. Formatting goes through
  their `Display` (`{:.2}` and `{:.3}`). Do not add a public accessor to `till-core`.
- Do not modify `till-core` or `till-store`. They are merged and reviewed; if this
  plan appears to need a change there, that is a finding to raise, not a licence.
- **Module paths matter.** `till-core`'s `lib.rs` re-exports only `basket`, `line`,
  `money` and `tender` items at the root. The code tables and the scanner are **not**
  re-exported, so they are reached as `till_core::codes::{TaxType, PmtTyCd, RcptTyCd}`
  and `till_core::scan::{classify, Scanned, EmbeddedMode, ScanError}`, and the line
  cap as `till_core::basket::MAX_ITEM_SEQ`. `till-store` does re-export `Store`,
  `CachedProduct`, `NewSale`, `SaleHandle`, `VsdcReceipt` and `Counter` at its root.

## Out of Scope — state this, do not build it

- The signed `.msi`, the update channel and lane-to-org pairing. Windows-specific,
  belongs to 2a-install.
- The real VSDC/EBM client. Phase 3. This plan builds the `FiscalPort` **trait** and a
  simulated implementation; the lane honours C1 against it.
- Refunds, suspend/resume, X and Z reports, shift open/close, buyer TIN capture.
  Later 2d slices.
- Real hardware drivers. Traits and simulated implementations only.

## Review Focus

Five things the spec implies that no task's happy path exercises. Each has a test
assigned to the task that owns the code.

1. **A scan arrives while the fiscal port is down.** Keystrokes during a hard-stop
   must not quietly accumulate into a sale the cashier cannot complete. (Task 8)
2. **A barcode the catalogue does not have.** The cashier is told; nothing is guessed
   and no line is added. (Task 7)
3. **The 999-line cap is reached mid-sale.** `BasketError::TooManyLines` must surface
   as a readable instruction, never a panic. (Task 7)
4. **Tender below the amount due, and over-tender on a non-cash code.** Neither may
   settle; change is cash-only and capped by cash received. (Task 8)
5. **The printer fails after the sale is confirmed.** The sale is already fiscally
   done — it must stay done and the receipt must be reprintable, not lost. (Task 9)
