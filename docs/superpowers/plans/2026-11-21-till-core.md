# Till Core Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Build the till's UI-agnostic Rust core — the fiscal arithmetic that produces an RRA-valid `saveSales` payload, and the local SQLite store that makes a sale exist exactly once with a gapless invoice number.

**Architecture:** A `cargo` workspace at `till/` with two crates. `till-core` is pure, synchronous, I/O-free: money and quantity newtypes, the RRA code tables, VAT extraction, basket lines, per-band totals, discounts, tender, and barcode resolution. `till-store` wraps SQLite via `sqlx` and owns the catalogue cache, the gapless per-`bhfId` `invcNo` sequence, the sale mirrors and the cloud outbound queue. Neither crate knows whether the UI is a webview or a native renderer, which is what makes this plan safe to build while §9 Q6 is open (see Ruling R35).

**Tech Stack:** Rust (edition 2024, `rust-version = "1.85"`), `rust_decimal` for exact money, `sqlx` + SQLite, `tokio`, `thiserror`, `serde`. No Tauri, no React, no hardware, no network in this plan.

**Spec:** `docs/superpowers/specs/2026-11-20-supermarket-retail-design.md` (§5 constraints, §6.4 language, §7 architecture and the sale end-to-end, §8 Phase 2)

**RRA reference (authoritative, now vendored):**
- `docs/reference/rra/vsdc_specification_document_v1.0.4__2022.pdf` — §3 API, §4.1 Tax Type, §4.8–4.14 code tables, `saveSales` JSON sample
- `docs/reference/rra/20180328_tspe_cis_v4.pdf` — CIS technical specification (C1 hard-stop)
- `docs/reference/rra/osdc_documentation_v1.0.1_2022-04-08.pdf`
- Pre-extracted text alongside each: `vsdc.txt`, `cis.txt`

## Scope boundary — what this plan deliberately excludes

Phase 2 in the spec is four subsystems (2a shell/install, 2b hardware, 2c local store, 2d the lane). This plan is **2c plus the fiscal core of 2d**, and nothing else. Excluded, with the reason:

| Excluded | Why it is not here |
|---|---|
| Tauri shell, signed `.msi`, update channel (2a) | Blocked on C9 / §9 Q6 — unverifiable from here. Also needs a Windows code-signing certificate that does not exist, and a Windows installer cannot be verified from macOS. |
| The lane screens (2d UI) | The spec makes the Tauri-vs-native decision precede screen work. |
| ESC/POS, scale, scanner driver, drawer kick (2b) | Independent subsystem; its own plan. Nothing here depends on it. |
| `FiscalAdapter` / `EbmRwandaAdapter`, VSDC HTTP calls (Phase 3) | Needs Test VSDC access (§9 Q2). This plan builds the *payload* and the *states*, not the conversation. |
| Scan-to-tender speed gate | Needs a pilot shop and a running Microinvest (§9 Q7). |

Everything in this plan is required identically whichever way C9 resolves.

## Global Constraints

- **C1 — offline selling is prohibited.** A sale is complete only after the VSDC responds and the receipt prints. This plan therefore never marks a sale complete on its own; it may only move a sale into `AwaitingVsdc` and record the outcome it is given.
- **C5b — the code tables are RRA's.** Tax type is exactly `A` `B` `C` `D` (VSDC §4.1: `A`=A-EX exempt, `B`=B-18.00%, `C`, `D`). Payment method is exactly **seven** codes (VSDC §4.10): `01` CASH, `02` CREDIT, `03` CASH/CREDIT, `04` BANK CHECK, `05` DEBIT&CREDIT CARD, `06` MOBILE MONEY, `07` OTHER. Tax rates as sent: `taxRtA=0`, `taxRtB=18`, `taxRtC=0`, `taxRtD=0`.
- **VAT is extracted from inclusive prices, never added.** `taxAmt = taxblAmt × rate / (100 + rate)`, rounded half-up to 2 decimal places. `totAmt == totTaxblAmt`. Header `totTaxAmt` is the **sum of line `taxAmt` values**, not a recomputation from the total. (Ruling R36; evidence in the task that implements it.)
- **Money is `Decimal(_, 2)`; quantity is `Decimal(_, 3)`.** Matching the cloud schema. Never `f64` for either, and never a float column in SQLite — money and quantity persist as exact decimal **TEXT**.
- **Currency RWF, timezone Africa/Kigali.** Dates on the wire use the VSDC formats: `cfmDt`/`stockRlsDt` `yyyyMMddhhmmss`, `salesDt` `yyyyMMdd`.
- **`invcNo` is gapless per `bhfId` and lives only in the till's own SQLite** (§7 step 4). The cloud's per-org `InvoiceSequence` does not serve the lane.
- **No `sqlx` compile-time macros.** Use the runtime `query_as`/`query` API, so building never requires a live `DATABASE_URL`. `sqlx::migrate!` for migrations is fine.
- `cargo fmt --check`, `cargo clippy --all-targets -- -D warnings` and `cargo test` must all pass at the end of every task.

## Review Focus

Five input classes the spec implies but that no task's own happy path exercises. Each has its test added to the task that owns the code.

1. **Rounding residue across bands.** A basket where `Σ line taxAmt` differs from the band total recomputed from `Σ taxblAmt` — sum-of-lines must win, and `totAmt` must still equal `totTaxblAmt`. *(Task 6)*
2. **A basket discount that does not divide evenly.** Apportioning a whole-basket discount across lines leaves a sub-unit residual; the apportioned amounts must still sum exactly to the discount, and no line may go negative. *(Task 7)*
3. **Exempt and standard-rated goods in one basket.** Band A must contribute to `taxblAmtA` and `totTaxblAmt` while adding exactly zero tax, with `taxRtA` sent as `0`. *(Task 6)*
4. **Interruption between `invcNo` allocation and the VSDC reply.** A crash or refusal must leave neither a gap in the sequence nor a second sale on the same number; a retry must reuse the number. *(Tasks 11, 12)*
5. **A weight-embedded barcode that disagrees with the catalogue.** When the embedded price and the catalogue price differ, exactly one must win and it must be the same one every time. *(Task 9)*

### Task 4: VAT extraction from inclusive prices

This is the single most compliance-critical function in the plan, and it is deliberately one function so a correction is one line.

**Evidence for the convention** (VSDC spec v1.0.4, `saveSales` JSON sample and the stock samples):

| `taxblAmt` | sample `taxAmt` | `× 18/118` |
|---|---|---|
| 200,000 | 30,508 | 30,508.47 |
| 50,000 | 7,627 | 7,627.12 |
| 1,800,000 | 274,576.27 | 274,576.271 |
| 660,000 | 100,677.97 | 100,677.966 |

and in that same sample `totTaxAmt` is `38135`, which is `30508 + 7627` exactly — the header tax is the sum of the lines. `totAmt` equals `totTaxblAmt` (250,000) in every sample, confirming both are gross. Note the sample's own `taxAmtB: 94576` is inconsistent with its own lines and with `totTaxAmt`; it is a documentation error and the line sum is authoritative.

**Decimal places.** The `saveSales` sample truncates to whole francs (`30508`) while the stock samples in the same document carry two places (`274576.27`, `100677.97`), and the declared field format is `18,2`. This plan keeps two places, because the format permits it and the stock samples prove the VSDC accepts it. **Open question for RRA:** whether a Rwandan receipt should show whole francs, since no subunit circulates. That is a presentation decision for the receipt composer in Phase 3, not an arithmetic one here, and `extract_tax` is the single place it would change.

- Create: `till/crates/till-core/src/tax.rs`
- Modify: `till/crates/till-core/src/lib.rs`

**Interfaces:**
- Consumes: `Money` (Task 2), `TaxType` (Task 3).
- Produces: `extract_tax(taxbl: Money, band: TaxType) -> Money` — the VAT contained *within* `taxbl`, rounded half-up to 2 dp.

### Task 5: Basket line amounts

**Files:**
- Create: `till/crates/till-core/src/line.rs`
- Modify: `till/crates/till-core/src/lib.rs`

**Interfaces:**
- Consumes: `Money`, `Qty`, `TaxType`, `extract_tax`.
- Produces:
  - `struct BasketLine { item_seq: u16, item_cd: String, item_cls_cd: String, item_nm: String, bcd: Option<String>, qty: Qty, prc: Money, tax_ty_cd: TaxType, discount: Option<LineDiscount> }`
  - `enum LineDiscount { Percent(Decimal), Amount(Money) }` — mirrors the cloud's `DiscountKind`.
  - `struct LineAmounts { sply_amt: Money, dc_rt: Decimal, dc_amt: Money, taxbl_amt: Money, tax_amt: Money, tot_amt: Money }`
  - `BasketLine::amounts(&self) -> Result<LineAmounts, LineError>`
  - `LineError::{ NonPositiveQty, DiscountExceedsSupply }`

Field names are the VSDC wire names on purpose: this struct is what Phase 3 serialises, and a rename between here and there is a defect waiting to happen.

Definitions, from the sample payload: `sply_amt = qty × prc`; `dc_amt` is the discount in money; `dc_rt` is that discount as a percentage of `sply_amt` (RRA carries both); `taxbl_amt = sply_amt − dc_amt`; `tax_amt = extract_tax(taxbl_amt, band)`; `tot_amt = taxbl_amt` (the sample shows line `totAmt` equal to line `taxblAmt`, both gross).

### Task 7: Whole-basket discount, apportioned across lines

RRA has no header-level discount field — only per-line `dcRt`/`dcAmt`. A basket discount must therefore be pushed down onto the lines before totals are taken, and the pushed-down amounts must sum exactly to the discount.

**Files:**
- Modify: `till/crates/till-core/src/basket.rs`

**Interfaces:**
- Consumes: `Basket`, `LineDiscount`, `LineAmounts`.
- Produces: `Basket::set_basket_discount(LineDiscount)`, and `Basket::apportioned_lines(&self) -> Result<Vec<(BasketLine, LineAmounts)>, BasketError>` which `totals` now calls. New error `BasketError::DiscountExceedsBasket`.

Apportion by each line's share of `sply_amt`, rounding each share to 2 dp, and give the **last** line the residual so the sum is exact. The largest-remainder alternative distributes error more evenly but makes the result depend on sort order; last-line residual is deterministic and auditable on a printed receipt.

### Task 9: Barcode and PLU resolution

**Files:**
- Create: `till/crates/till-core/src/scan.rs`
- Modify: `till/crates/till-core/src/lib.rs`

**Interfaces:**

- Produces:

  - `ScanError::{ Empty, NonNumeric, BadLength(usize), BadCheckDigit { expected: u8, got: u8 } }`

Weight-embedded barcodes are EAN-13 in the in-store prefix range `02` and `20`–`29`: digits 3–7 are the item reference and digits 8–12 carry either an embedded weight (5 digits, grams) or an embedded price, with the last digit the check digit. Which of the two a shop uses is a per-shop setting, so `classify` reports what it found and does not guess.

**Review Focus 5 is resolved here by ruling:** when a weight-embedded barcode carries a price and the catalogue also has one, **the embedded price wins**, because the scale that printed the label already weighed the goods the customer is holding. The catalogue price is used only when the barcode carries a weight instead of a price. The test below pins that direction so a later change is visible.

### Task 11: Gapless `invcNo` allocation

**The ruling this task implements (R38).** The sequence must be gapless, yet the number is consumed before the VSDC is told anything, so a refusal or a power cut between the two would otherwise burn a number. Therefore: allocating the number and inserting the sale row in state `AwaitingVsdc` happen in **one** transaction, so either both or neither survive a crash. A VSDC failure leaves the sale in `AwaitingVsdc` and the **same** number is retried; a number is never reallocated. On a retry the VSDC may answer `994` ("There is an overlapped Data", VSDC §4.14), which means it already holds that invoice — that is success, not an error, and the caller proceeds to print. Because an unresolved `AwaitingVsdc` sale blocks the sequence, the store must be able to find it at startup.

**Files:**

- Modify: `till/crates/till-store/src/lib.rs`

**Interfaces:**
- Consumes: `Store`.
- Produces:
  - `Store::allocate_invc_no(&self, bhf_id: &str) -> Result<i64, StoreError>` — for callers that only need the number (used inside Task 12's transaction).
  - `Store::pending_sale(&self, bhf_id: &str) -> Result<Option<PendingSale>, StoreError>` where `PendingSale { id: String, invc_no: i64 }`.
  - `StoreError::SequenceBlocked { invc_no: i64 }` — returned when a new allocation is attempted while an `AwaitingVsdc` sale exists on that branch.

### Task 12: Persist a sale and queue it for the cloud, in one transaction

**Files:**

## Rulings recorded while writing this plan

- **R35 — Phase 2 splits; the UI-agnostic core goes first.** C9 (§9 Q6) is unverifiable from here and the spec makes it the gate on Tauri versus a native UI. But that fork is confined to the UI layer: the spec itself puts basket, pricing and tender in the Rust core "not the webview" (§6.4), the hardware behind traits with simulated implementations (§8-2b) and the store in `sqlx` (§8-2c). None of those changes by a line either way, so building them now wastes nothing and unblocks the day. *Cost if wrong:* only if §6.1-C itself were reversed — i.e. no installed application at all — would this work be lost, and that decision is already made and recorded.
- **R36 — VAT is extracted from inclusive prices, and the header tax is the sum of the lines.** `taxAmt = taxblAmt × rate/(100+rate)` half-up to 2 dp; `totAmt == totTaxblAmt`; `totTaxAmt = Σ line taxAmt`. Evidence: the VSDC v1.0.4 `saveSales` sample's own lines (200,000→30,508 and 50,000→7,627, summing to the header's `totTaxAmt` of 38,135) and the stock samples' exact 274,576.27 and 100,677.97. The sample's `taxAmtB: 94576` contradicts its own lines and is a documentation error. *Cost if wrong:* every receipt's tax line is wrong and certification fails — which is why it is one function with the sample figures as its tests.
- **R37 — `TenderMethod` was missing a code.** VSDC §4.10 defines seven payment methods; the design spec's C5b listed six and Phase 1 implemented six. Task 1 adds `OTHER` (`07`). *Cost if wrong:* none; the code exists in the published table.
- **R38 — gapless `invcNo` survives a crash by holding the sequence, not by skipping.** Allocation and the `AwaitingVsdc` sale row are one transaction; a failure retries the same number; an unresolved sale blocks the next allocation. A `994` from the VSDC on retry means it already holds the invoice and is success. *Cost if wrong:* if RRA would rather see a gap than a retried number, this inverts — but a gap in a fiscal sequence is the thing certification actually checks for.
- **R39 — change is cash-only.** Over-tendering a card or mobile-money payment is refused rather than resolved as change, because the till cannot hand back money it never took. *Cost if wrong:* a cashier workflow needs a second step for a genuine partial refund, which is a lane-UI concern, not an arithmetic one.
- **R40 — an embedded barcode price beats the catalogue price.** The label was printed by the scale that weighed the goods in the customer's hand. *Cost if wrong:* a stale scale price overrides a corrected catalogue price; the test pins the direction so reversing it is one change.
- **R41 — the RRA specifications are vendored into the repository.** `docs/reference/rra/` now holds the three PDFs the design spec cites plus extracted text. They were cited but not committed, so every value in this plan would otherwise have been unverifiable at execution time. *Cost if wrong:* ~6 MB of binaries in git history.
