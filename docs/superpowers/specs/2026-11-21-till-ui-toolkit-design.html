Design decision · amends §6.4 and C9

The lane is a pure-Rust desktop app

Phase 2 was parked on a fact nobody can obtain. Rather than keep waiting for it, this removes the dependency that made the fact matter.

Awaiting your sign-off 2026-11-21 Unblocks 2a + 2d Skin: Cloud & Azure Core already merged · f16913f
01 — Why now

C9 is unanswerable, not just unanswered

The spec made “verify C9 against real pilot hardware” the first action of Phase 2a. But §9 Q7 is still open — there is no pilot shop. There is no till to read an OS build number off, and no one to ask.

So the gate is not waiting on effort; it is waiting on a shop that does not exist yet. Left alone, Phase 2 stays parked indefinitely while the decision it guards — Tauri versus a native UI — keeps getting more expensive to reverse, because the thing at risk is 2d: scan, weighed items, voids, discounts, suspend and resume, mixed tender, refunds, shift open and close, X and Z reports. That is the largest surface in the project and the worst one to rebuild.

The way out is not to answer C9. It is to stop depending on the answer.

02 — Approaches

Three ways to put a screen on that counter

OPTION 1

Tauri 2 + Shelf Edge React

Reuses the existing skin and idiom directly. But it needs WebView2 and a Windows 10 floor we cannot verify, and it adds an IPC boundary to design between webview and core.

The runtime can be bundled (offlineInstaller ~127 MB, fixedVersion ~180 MB), which removes the missing-runtime half of the risk — but not the OS floor.

Rejected — unquantifiable risk, landing on the costliest phase
OPTION 2

Local agent, UI in the installed browser

Our Rust process on the counter serves the lane UI from 127.0.0.1. Kills C9 outright, reuses the skin as-is, smaller install than Tauri, and keeps the locally-installed-invoicing-system story §9 Q1 leans on.

Costs: a browser is weakly locked down — F11, tabs, navigating away — and a localhost endpoint is a security surface needing a token and strict CORS.

Rejected — desktop chosen over a browser lane
OPTION 3

Pure-Rust desktop UI

No webview, no runtime, works below the Windows 10 floor, and one language shared with the already-merged till-core and till-store — which deletes the IPC seam §10 left open.

Costs a skin rebuild and hand-built layout instead of CSS. Affordable exactly because Shelf Edge is flat.

Chosen
03 — Why the rebuild is cheap

The skin was never the expensive part

§6.4 treated “the skin is rebuilt rather than reused” as the cost that made a native UI the fallback rather than the default. That cost is mispriced — though the argument had to be re-checked when the skin changed the next day.

The original argument expired, so here is the replacement

I first argued the port was cheap because Shelf Edge was flat: 2px corners, no shadows. Cloud & Azure is softer — 14px rounding — so inheriting that argument would have been dishonest. Re-checked against what egui actually draws:

  • Rounding is free. Rounded rectangles are a primitive; a 14px corner costs exactly what a 2px one does.
  • Hairlines are free, and this skin leans on a 1px #E2EBF4 border rather than heavy rules — which is the grammar of the references it came from.
  • Soft shadows are the one weak spot, so the panels carry their depth in hairlines and a tinted second surface instead. More minimal anyway.
  • Two typefaces — Inter and JetBrains Mono — both TTFs that embed straight into the binary.

What would genuinely hurt is a shadow-heavy, layered-glass skin. That is the one direction this decision rules out, and Cloud & Azure is not it.

04 — Decided

The how, as settled

ItemDecision
Toolkitegui + eframe. Immediate mode, mature, embeds fonts directly, and draws flat fills and tabular numerals well.
FontsArchivo and IBM Plex Mono embedded as TTFs in the binary — no font installation on the counter.
TokensPorted to Rust constants from globals.css, so the lane and the back office cannot drift silently.
Not icedA reasonable retained-mode fallback if hand-built layout proves painful. Held in reserve, not chosen.
Not SlintTechnically well suited to kiosk and touch, but licence-encumbered for a commercial product (GPL or paid). Needs a commercial decision, so it is flagged rather than chosen.
Not DioxusDesktop renders in a webview — it reintroduces precisely what this decision removes.
2b hardwareTraits with simulated implementations against a generic ESC/POS profile. No model-specific quirks until a real shop exists.
§10’s open item resolves itself

The spec says to find out which printers and scales Kigali supermarkets own before choosing. With no pilot shop there is nothing to find out — so building generic is the answer, not a deferral. This is what 2b already prescribed.

05 — The gate we lose

Beating Microinvest is unmeasurable right now

§4’s sharpest quality bar — scan-to-tender must beat Microinvest on the same hardware — needs a pilot shop and a running Microinvest (§9 Q7). We have neither, so the gate cannot be run. I am not dropping it; I am proposing a proxy we can measure on any machine today, so the real gate is a comparison rather than a rebuild when a shop appears.

PathBudgetWhy this one
Keystroke → line on screen< 50 ms A cashier keying a PLU feels anything slower as lag.
Scan → line committed< 100 ms Covers the catalogue lookup and the basket arithmetic.
Tender → receipt bytes out< 300 ms The queue at the till is what the shop actually judges us on.
Cold start< 2 s Shift open happens under pressure; it is also where a webview taxes you.
These four numbers are my proposal, not the spec’s

Nothing in the spec sets them. They are mine to be corrected — the point is that they are instrumented from the first screen, so there is a number to argue with instead of an impression.

06 — Left to the builder

Open, deliberately

  • egui widget decomposition, and where lane state lives relative to till-store.
  • The token and font port mechanics, and how drift from globals.css gets caught.
  • Table rendering for the X and Z reports.
  • Touch target sizing, subject to the latency budget above.
  • Which generic ESC/POS profile is the default, and how the simulated devices are driven in CI.
