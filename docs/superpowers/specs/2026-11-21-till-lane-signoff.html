01 — Read this first

The process missed the thing you found in a minute

You ran it, and in about sixty seconds found that the basket columns moved with the product name. 107 passing tests and three clean reviews had not caught it — because nothing in the suite can see a screen.

That is the honest boundary of what this produced. It can prove the till does not sell offline, does not burn invoice numbers, and prints a compliant receipt. It could still hand you a table whose columns wander.

What changed as a result

The fix carries a non-visual pin: a test that renders a row in a real egui frame with three different product names and asserts every cell's left edge is identical. Verified against the old code, where the edges drifted 20–60px.

02 — The worst defect was mine

Reprint was printing a second original

CIS §7.18, verbatim: "print only one original receipt. Reprint shall have a watermark with mention Copy." Our reprint replayed the retained bytes, so a duplicate printed as NS with its own verifiable QR. Two individually verifiable originals for one sale.

It came from my Task 9 brief — "a reprint must emit byte-for-byte what the original attempt composed" — on the reasoning that the customer's copy must match the fiscal record. That reasoning was wrong.

It survived three reviews. The task review and the re-review both confirmed "no path recomposes" — stating the defect as a success — because both were checking the code against my brief. The final review caught it only because I told it the specification outranks the plan and pointed it at the vendored documents.

Task 5 had already built the COPY banner and the CS label. The capability existed; nothing ever called it.

03 — Also fixed before merge

Two things the till was asserting without knowing

A misleading error at the worst moment

One Store variant served six call sites with a message written for scanning. A confirm_sale failure — customer paid, RRA holds the sale, nothing printed — told the cashier "The catalogue could not be read. Try the scan again." Now eight distinct operations; the confirm path says "Do not ring the items again."

A status chip that knew nothing

"VSDC ONLINE" was inferred from screen() != HardStop, not from contact. It stayed green through an entire basket during an outage. It now reports the last known outcome in the past tense, and claims nothing about current connectivity.

Lint suppressions hiding real warnings

Eight module-wide allow(dead_code) were hiding 15 genuine warnings. Replaced with narrowly scoped expect(dead_code), which the compiler retires once an item gains a caller.

04 — Rulings I made on your behalf

Forty-one decisions, and what each costs if wrong

Seven from the pre-flight scan of my own plan, thirty-four during execution. Read the ones marked consequential first — those changed what the software does rather than how it is arranged.

#Decision · why · cost if wrong
R1Lane methods are async; the UI owns a tokio runtime. till-store's API is async throughout, so my sync signatures physically could not call it. If wrong: the UI carries a block_on per transition it could have avoided.
R2Task 11 defines Devices. It is wiring; Task 3 owns the traits, not the aggregate. If wrong: the struct moves one file.
R3Add SimMode::Overlapped so RRA's 994 is constructible rather than dead code. If wrong: one extra simulator branch.
R4Task 8 consumes receipt::compose — my brief omitted the interface. If wrong: nothing; documentation.
R5Task 10 also modifies lane.rs, which its own Files block omitted. If wrong: nothing.
R6Scale and ScanSource ship unwired. The design doc mandates the full 2b trait set; a keyboard wedge needs no polling. If wrong: two traits wait for hardware that never arrives and get deleted.
R7Task 11 owns the demo catalogue, seeded with the mockup's products. If wrong: the seed moves to a fixtures module.
8 ⚑Consequential — rwf rounds half-up away from zero; it does not truncate, and never prints -0. till-core's whole_francs is half-up, and that function produces the amount actually committed — truncating would show a figure one franc below what the database recorded. If wrong: display drift on an input that should not occur.
9init() stays bare ESC @; code page is a separate call. Without an explicit selection the output depends on each printer's power-on default. If wrong: two surplus bytes per receipt.
10 ⚑Consequential — control characters in product names become ?. A raw ESC or GS in a staff-typed name would otherwise be executed by the printer as a command. Command injection via the catalogue; the implementer added this unasked. If wrong: a legitimate control character is lost.
11QR module size 6 and error correction M stand as unconstrained. Checked the primary source: CIS §7.24.7 specifies only the payload. Recorded as a question for RRA, not as verified. If wrong: a scanner struggles; revisit on real hardware.
12double_height = GS ! 0x01 is correct — the low bits select the height multiplier. If wrong: the banner prints at normal size.
13 ⚑My brief was wrong: receipt types are SalesTyCd, not RcptTyCd (Sale/Refund only), and the banner is PROFORMA not "PRO FORMA". The label is the §5.3 combination — NS, NR, CS, CR, TS, TR, PS — from both enums. If wrong: the receipt label is unreadable to the VSDC.
14"THIS IS NOT AN OFFICIAL RECEIPT" goes below the totals. §11's normative text says below; only the sample puts it above. Text outranks sample. If wrong: a misplaced notice on non-official receipts.
15 ⚑Consequential — refunds are refused outright. §14 requires a referenced receipt number the input cannot carry. A loud refusal beats a receipt missing a mandated field. If wrong: no refunds until a later slice — which is the truth either way.
16The CIS date and time must print beside the CIS receipt number; every sample shows it. If wrong: one unused field.
17 ⚑Consequential — compose is fallible, and the panicking variant removed. Keeping both invited a caller to reach for the one that aborts the till mid-sale. My brief specified the infallible signature. If wrong: nothing; no caller existed yet.
18The RRA logo (§7.29) and the watermark (§11) are deferred and documented. Both need raster support the encoder lacks. If wrong: certification meets two known, written-down gaps.
19 ⚑Money prints as whole francs despite the spec's samples showing 1000.00. The sample illustrates; RWF has no subunit; the VSDC receives exact decimal strings in the Phase 3 payload, which is where format compliance bites. Logged as an RRA question. If wrong: a display-format change on the receipt.
20Item rows carry the full tax label (A-EX, B-18.00%), not a bare letter. §7.22 requires "the tax label" and four samples render it so. Promoted from a Minor the reviewer called a sample convention. If wrong: a more verbose item row.
21Bound the QR fields so the encoder's last reachable panic became provably unreachable. If wrong: an over-long signature is refused rather than printed.
22 ⚑⚑Most consequential — a product with no RRA item classification is REFUSED, not defaulted. vsdc.txt:1086 marks itemClsCd Required=Y from an RRA-managed vocabulary, so the sample default would have filed a false mandatory tax classification for every unconfigured product. If wrong: products cannot be sold until the back office fills the field — a data-quality problem surfaced rather than silently misreported.
23 ⚑Consequential — Err is only for faults the cashier cannot act on. Unknown barcode, bad scan, full basket return Ok with a notice. "This milk is not in the catalogue" is a business outcome, not a program failure. If wrong: the UI inspects a notice where it might have matched a variant.
24 ⚑Ratified four guards the implementer added unasked: refusing a weighed product scanned as a plain barcode (it would sell as exactly one kilo), a Price-mode label overriding the catalogue price, refusing a zero-weight label, and pricing a line before it spends a sequence number. If wrong: four refusals that could have been sales.
25 ⚑⚑Most consequential — on RRA 994 the sale is abandoned and the lane KEEPS SELLING. 994 means the VSDC already recorded that number, so nothing is recoverable — but the device is plainly reachable, so C1's offline condition does not apply and halting would be wrong. If wrong: a shop keeps trading where it should have stopped, or one basket is re-keyed unnecessarily.
26settle returns Ok(None) when no sale completed, rather than inventing a result. If wrong: callers match on an Option they need not.
27 ⚑Consequential — the pending-sale freeze stays, and so does its escape hatch. A sale left awaiting holds a live invoice number, so trading over it would orphan the number; without an escape a permanent rejection wedges the lane. The hatch has no supervisor gate — logged for a later slice, and auditable today since the number is retired with a recorded reason. If wrong: a cashier can void a pending sale without a second party.
28 ⚑A confirm retry never re-sends the sale. Re-sending returns 994 and burns the number for nothing. The implementer reasoned this out unprompted; a comment now records why. If wrong: a burned number per confirm failure.
29A printer or drawer fault after confirmation leaves the sale confirmed. The fiscal record is the sale; paper is not. If wrong: a paid sale would be rolled back over a paper jam.
30 ⚑Consequential — the hard stop needed an exit. Without one the lane recovered only by restarting. §24.7.9 requires stopping on the error AND resuming once cleared, so an exit is part of the requirement. If wrong: a cashier leaves the stop early and the next settle stops again.
31 ⚑Consequential — the lane can serve a second customer. Settled was terminal; no remaining task owned the transition, and my brief's own test hid it by building a second lane. If wrong: nothing; it was unusable without this.
32 ⚑⚑Most consequential — a sale stranded by a crash is detected at startup and may only be CANCELLED, never retried. Without a "sent to VSDC" marker we cannot know whether RRA received it, so re-sending risks a duplicate fiscal record. Cancelling may leave a record at RRA with no local counterpart — a reconciliation problem, strictly better than a till nobody can use. If wrong: an abandoned sale that RRA did record needs manual reconciliation.
33 ⚑A lane that cannot read its own database does not open. Rejected the alternative of showing the hard-stop screen: that means "the VSDC is unreachable, wait", which would send a shop to check a healthy network. If wrong: one more Result at construction.
34sqlx as a dev-dependency so a test can read the sale row directly and prove Confirmed — asserting the screen would pass even if the sale had been rolled back. If wrong: a test-only dependency.
35The retained receipt survives the next customer. Clearing it earlier destroys the reprint exactly when it is wanted — the customer who returns a minute later. If wrong: a previous receipt is reprintable slightly too long.
36A settle that completes no sale records no timing, and neither does one whose print failed. The budget is "tender to bytes out"; a run producing no bytes has nothing to time. If wrong: the measurement is polluted by faster failure paths.
37The latency caveats are recorded, not just the numbers. Two of the four paths measure only a slice (no frame render, no process start), and the 300 ms budget was measured against a VSDC that answers instantly. If wrong: the numbers get quoted as if they measured the whole journey.
38Quantity splits: the screen shows 2, the receipt keeps three places. RRA's own sample shows 1.00 — a third convention — so the receipt keeps what a passing test pins and the question goes to RRA. If wrong: the receipt quantity format changes.
39 ⚑If the original never reached the printer, the first reprint IS the original. §7.18 says print one original — if none printed, none has been — and §7.28 independently requires re-printing after a paper-out. The implementer proposed it; the final reviewer verified it is applied consistently through one flag. If wrong: a jammed customer receives only a COPY.
40A COPY still carries its QR. The payload is the identity of the one fiscal record, so scanning a copy resolves to that record and correctly reports it valid. §15.1's COPY sample already prints the same data in readable form. If wrong: a scannable duplicate re-creates §7.18's problem in subtler form.
41 ⚑The COPY counter deviation is deferred but WRITTEN INTO THE CODE. A reprint carries the original's counter under a CS label where §7.25.1 wants a per-type series. A true CS series needs a VSDC round-trip, so it belongs with Phase 3 — but this workspace is deleted at merge, so receipt.rs is the only durable home for a known deviation. If wrong: certification meets an undocumented CS counter.
05 — Shipping with these known gaps

Written into the code, not just this page

  • No RRA logo and no watermark (§7.29, §11) — both need raster image support the encoder does not have.
  • A reprint carries the original's receipt counter under a CS label. Phase 3 work.
  • The retained receipt lives only in memory — a crash after a paper jam loses a paid customer's legal document. Closing it needs a column on the sale row, and this plan froze till-store.
  • The hard stop fires only at settlement. §24.7.9 says "whenever a communication error appears"; §24.7.8's CMD: STATUS heartbeat is a later slice.
  • SalePayload carries 5 of roughly 30 fields saveSales requires, and no item list — Phase 3 will re-cut the trait rather than implement it.
  • F2–F7 are drawn muted: discount, suspend, resume, refund, buyer TIN, X/Z reports. Later 2d slices.
  • Watch this one: resuming from a hard stop clears the tenders. Safe while cash is the only tender key — a double-charge risk the day a card tender lands.
06 — Questions for RRA

Five things I refused to guess

  • Does the printed receipt require money at two decimals, as the samples show, or are whole francs acceptable?
  • In the §7.24.7 QR, is "sdc_receipt_number" rcptNo or totRcptNo?
  • Are internal data and signature dashed or raw inside the QR?
  • What rates and labels do tax bands C and D carry? The samples show only A and B.
  • Does the receipt require quantity at two decimals, as cis.txt:298 shows?

These join the four still open from the previous phase, including the sharpest one: whether lastInvcNo means last-used or next-to-issue. An off-by-one there makes a reinstalled till fail its first sale unrecoverably.
